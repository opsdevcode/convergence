# Anti-patterns

**Status:** Named for v0.1 so they cannot be mistaken for the model.
Full write-ups remain later work (roadmap v0.7).

## Convergence is not organizational consolidation

Convergence does **not** mean: eliminate Platform, SRE, or Security;
collapse specialists into Product; create universal full-stack teams;
centralize all engineering; mandate one platform or one implementation;
create a "Convergence Engineering" silo; or create a VP or team that
becomes the routing layer for Convergence.

**Convergence cannot be delegated to a Convergence function.**

## Failure modes already named elsewhere

- Portal as ticket router
- "You build it, you run it" without encoded reliability or security
- Capability as a team rename with the same queue
- A capability that exists to justify its realization
- Agent with org-wide credentials and no contracts
- Treating invocation as authority
- Measuring platform success only as developer satisfaction or adoption
- Treating Converged Engineering as a synonym for Platform Engineering or
  DevOps
- Treating Convergence as a new specialty or "Convergence Engineering" team
- Treating a capability catalog as a complete solution to organizational
  problems
- Claiming specialists are no longer needed
- Treating human-realized capabilities as immature and automation as mature
- Requiring a platform, catalog, or graph database to "do Convergence"
- Requiring one enterprise graph or one global capability taxonomy
- Treating every handoff, approval, or organizational boundary as waste
- Maximizing reuse, abstraction, or self-service as if that were the score
- Contracts or models treated as perfect representations of reality

An anti-pattern page should describe why the move is tempting, what it
costs, and what to do instead, without mocking the people who did the
tempting thing for a real reason.
