# Security

Security expertise remains. Threats do not care that you composed a graph.

## What does not disappear

- Threat modeling and abuse-case thinking
- Vulnerability and incident response
- Assurance, audit, and regulatory conversation
- Design review for novel systems
- The authority to say no when a capability would encode the wrong thing

## What changes

Governance and security controls should increasingly live in capability
**contracts and realizations** (policy, automation, continuous
verification) rather than existing only as approval gates. Novel
assessment remains a capability even when it is human-realized
(`AssessNovelSecurityArchitecture`).

Security engineers should help specify what compositions are allowed, what
evidence is required, and how verification runs as part of consumption.
Exception processes remain for the residual.

When security is only a queue, product teams learn to batch risk at the end.
When security is in the contract, the standard path is already constrained,
and security time goes to the exceptions and to improving the path.

## What this is not

Encoded security is not "the model will catch it" as a substitute for
engineering. Policy engines fail open or closed depending on how they are
built. Security specialists own those failure modes. Converged Engineering
does not argue for unattended production in the name of self-service.
