# Governance

This project starts as a **maintainer-led** body of knowledge. There is no
foundation, board, or formal membership. That may change if the work attracts
sustained independent contributors. Until then, maintainers are responsible
for conceptual integrity and for keeping the writing vendor-neutral.

## Maintainers

Maintainers review pull requests, accept or reject RFCs, and decide when a
version (v0.x, later v1.0) is tagged as a snapshot of the docs.

The current maintainer list lives with the repository hosting account. Update
this section when named maintainers are published.

## What maintainers optimize for

1. A coherent definition and set of terms
2. Honest scope: Convergence and Converged Engineering as proposed
   software-delivery ideas; capabilities as a mechanism; no claim to own
   historical uses of "Capability Engineering"
3. Vendor neutrality
4. Respect for specialized engineering work

Volume of documentation is not a goal.

## Decision types

| Change | Path |
| --- | --- |
| Editorial, examples, placeholders | Pull request |
| Foundational definitions (Convergence, Converged Engineering), principles, capability model, architecture, terminology | [RFC](rfcs/README.md) then pull request |
| License, governance model itself | RFC plus explicit maintainer agreement |

## RFC process

Significant conceptual changes use the process in [rfcs/README.md](rfcs/README.md).
An RFC can be accepted, deferred, or declined. Acceptance does not require
unanimous public consensus, but maintainers should record the rationale in
the RFC file.

## Evolution

If independent maintainers from multiple organizations join, this document
should be updated to describe:

- How maintainers are added or removed
- How deadlocks are resolved
- Whether a steering group is warranted

Do not invent those structures in advance.

## Conduct

[CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) applies to all project spaces.
Enforcement is a maintainer duty until a broader community process exists.
